# PRD — فروشگاه آنلاین ابزار احمدی (MVP)

نسخه: ۲.۰ (MVP) · وضعیت: آماده‌ی استقرار روی Vercel · زبان/جهت: فارسی، RTL

---

## ۱. خلاصه‌ی محصول

ابزار احمدی یک فروشگاه آنلاین ابزار و تجهیزات ساختمانی است که هم‌زمان یک پنل مدیریتی کامل (فروش حضوری، خرید از تأمین‌کننده، انبار، مالی، چک) دارد. کل پروژه Full-stack روی Next.js است و داده‌ها از طریق Route Handlerهای Next.js در فایل‌های JSON داخل ریپوی GitHub ذخیره می‌شوند.

**هدف MVP:** مشتری بتواند محصول را پیدا کند، سفارش ثبت و پرداخت کند و پیگیری کند؛ مدیر بتواند سفارش را تأیید، ارسال و حسابداری کند — بدون هیچ داده‌ی فقط-فرانت‌اندی.

## ۲. اهداف و معیارهای موفقیت

| هدف | معیار |
|---|---|
| ثبت سفارش آنلاین کامل | ثبت سفارش با آدرس و پرداخت (کارت‌به‌کارت) بدون خطا؛ سفارش در `sales.json` و اقلام در `sale-items.json` |
| یکپارچگی داده | هر تغییر موجودی/مالی/مشتری/سفارش در «یک commit اتمیک» انجام شود |
| قابلیت اتصال درگاه | افزودن درگاه واقعی فقط با پیاده‌سازی یک کلاس + env، بدون تغییر UI و دامنه‌ی سفارش |
| سئو | ایندکس‌پذیری صفحات محصول/دسته‌بندی، JSON-LD معتبر، sitemap/robots صحیح |
| امنیت پایه | جداسازی کامل مشتری/مدیر، عدم نشت اطلاعات داخلی (قیمت خرید، سفارش دیگران) |

## ۳. کاربران و نقش‌ها

- **مهمان:** مشاهده‌ی کاتالوگ، سبد خرید (ذخیره‌شده روی بک‌اند با کوکی مهمان).
- **مشتری (`CUSTOMER`):** ثبت‌نام/ورود، آدرس‌ها، علاقه‌مندی‌ها، ثبت سفارش، پیگیری سفارش، ترجیحات (تم).
- **مدیر (`ADMIN`):** دسترسی کامل به داشبورد. (نقش‌های SELLER/ACCOUNTANT/WAREHOUSE عمداً حذف شده‌اند.)

## ۴. دامنه‌ی MVP

### ۴.۱ فروشگاه (Storefront)
1. صفحه‌ی اصلی: اسلایدر، فروش ویژه، دسته‌ها، برندها، پرفروش‌ها (بر اساس فروش واقعی).
2. لیست محصولات: جستجو، فیلتر دسته/برند/موجودی/قیمت، مرتب‌سازی، صفحه‌بندی.
3. صفحه‌ی دسته‌بندی (`/categories/[slug]`) و صفحه‌ی محصول (`/products/[id]`) با گالری، مشخصات، محصولات مرتبط.
4. سبد خرید ذخیره‌شده در بک‌اند (مهمان یا کاربر) + ادغام سبد مهمان پس از ورود.
5. ثبت سفارش: آدرس ارسال (آدرس ذخیره‌شده‌ی قبلی خودکار پر می‌شود)، آپلود فیش (در حالت کارت‌به‌کارت)، یا هدایت به درگاه (در حالت آنلاین).
6. حساب کاربری: سفارش‌ها، وضعیت پرداخت و ارسال، کد رهگیری، نتیجه‌ی پرداخت آنلاین.
7. علاقه‌مندی‌ها (ذخیره در بک‌اند)، تم روشن/تاریک (ذخیره در بک‌اند برای کاربر واردشده).
8. صفحات اطلاعاتی: درباره ما، تماس، سوالات متداول (FAQ schema)، قوانین، حریم خصوصی.

### ۴.۲ پنل مدیریت
- داشبورد، گزارش‌ها (Recharts)، مرکز اعلان‌ها (وضعیت خوانده‌شده در بک‌اند).
- محصولات (گالری، تصویر اصلی، تأمین‌کننده‌ها)، دسته‌ها، برندها.
- POS فروش حضوری، فروش‌ها (تغییر وضعیت پرداخت، ارسال، چاپ فاکتور)، پیش‌فاکتور.
- خرید از تأمین‌کننده (نقدی/چکی)، انبار و تعدیل موجودی، مالی، درآمد/هزینه، چک‌ها (تاریخ جلالی)، مشتریان، تأمین‌کنندگان، کاربران، تنظیمات، لاگ فعالیت، مرکز داده.

### ۴.۳ خارج از دامنه (بعد از MVP)
درگاه پرداخت واقعی فعال‌شده، OTP پیامکی، کد تخفیف، نظرات و امتیاز کاربران، پنل چندنقشی، پایگاه داده‌ی واقعی (PostgreSQL).

## ۵. معماری

- **Next.js 16 (App Router) + React 19 + TypeScript + Tailwind 4**، بک‌اند در Route Handlerها.
- **لایه‌ی داده (`src/lib/github.ts`):** فایل‌های JSON در ریپوی GitHub (یا پوشه‌ی `data/` در حالت محلی).
  - `batchCommit`: چند فایل در یک commit اتمیک.
  - `mutateJson` / `withConflictRetry`: خواندن-تغییر-نوشتن با تلاش مجدد خودکار هنگام تداخل نوشتن هم‌زمان؛ هیچ به‌روزرسانی‌ای گم نمی‌شود.
  - فایل ناموجود در GitHub (404) مثل مقدار پیش‌فرض رفتار می‌کند.
- **احراز هویت:** کوکی امضاشده (HMAC-SHA256، HttpOnly)، رمز با scrypt، `AUTH_SECRET` در production اجباری، محدودیت نرخ (rate limit) روی ورود/ثبت‌نام/بازیابی.
- **دسترسی:** مشتری فقط `sales.create` دارد؛ همه‌ی `/api/admin/*` و `/dashboard` فقط ADMIN.
- **سرور اکشن‌ها:** خطاها با قالب `{ success, data | error:{code,message} }`.

### ۵.۱ مدل‌های داده (فایل‌های `data/*.json`)
`products, categories, brands, customers, suppliers, sales, sale-items, purchases, purchase-items, inventory, finance, expenses, incomes, checks, quotations, quotation-items, users, settings, carts, customer-events, activity-logs, payment-transactions` و فایل‌های جدید:

| فایل | کاربرد |
|---|---|
| `customer-addresses.json` | آدرس‌های ذخیره‌شده‌ی مشتری (حداکثر ۱۰ عدد، یک پیش‌فرض) |
| `wishlists.json` | علاقه‌مندی‌های هر کاربر |
| `user-preferences.json` | تم و وضعیت خوانده‌شدن اعلان‌ها |

## ۶. جریان‌های اصلی

### ۶.۱ ثبت سفارش آنلاین
1. اعتبارسنجی سرور: تعداد صحیح، موجودی، قیمت نهایی از روی محصول (قیمت کلاینت نادیده گرفته می‌شود)، آدرس، آدرس فیش.
2. **یک commit اتمیک** شامل: `sales`, `sale-items`, `products` (کسر موجودی)، `inventory`, `finance`, `customers`, `activity-logs`, `payment-transactions`.
3. کارت‌به‌کارت: وضعیت `PENDING_TRANSFER` → مدیر فیش را می‌بیند و تأیید می‌کند.
4. درگاه آنلاین: وضعیت `PENDING_PAYMENT` → هدایت به درگاه → بازگشت به `/api/payments/callback/[provider]` → تأیید سرور-به-سرور → `PAID`.
5. ایدمپوتنسی: ارسال مجدد همان `saleId` سفارش تکراری نمی‌سازد و فقط برای مالک (یا ادمین) برگردانده می‌شود.

### ۶.۲ تغییر وضعیت پرداخت (مدیر) — یک commit اتمیک
- به `PAID`: ثبت درآمد فروش در مالی (فقط یک‌بار)، کاهش بدهی مشتری، بستن تراکنش پرداخت.
- به `CANCELED`: برگشت موجودی + حرکت انبار، حذف درآمد فروش در صورت پرداخت‌شده بودن، وضعیت ارسال «لغو».
- از `CANCELED` به وضعیت فعال: کسر مجدد موجودی (با بررسی کافی بودن).
- حذف فروش: برگشت موجودی، حذف اقلام و درآمد مرتبط.

### ۶.۳ خرید از تأمین‌کننده
افزایش موجودی، به‌روزرسانی قیمت خرید، ثبت هزینه‌ی خرید و در صورت پرداخت چکی ثبت چک صادره — همه در یک commit.

## ۷. بستر درگاه پرداخت

`src/lib/payments.ts` با رابط `PaymentGateway { initiate, verify, online, isConfigured }`.

| پیاده‌سازی | وضعیت |
|---|---|
| `MANUAL_TRANSFER` | **فعال (پیش‌فرض)** — کارت‌به‌کارت + تأیید دستی مدیر |
| `ZARINPAL` | پیاده‌سازی شده، غیرفعال تا تنظیم env (نیاز به تست Sandbox) |
| `IDPAY` / `NEXT_PROVIDER` | ثبت‌نام‌نشده — کافی است کلاس نوشته و در `registry` اضافه شود |

**فعال‌سازی درگاه:** `PAYMENT_PROVIDER=ZARINPAL`، `ZARINPAL_MERCHANT_ID=...`، (اختیاری) `ZARINPAL_SANDBOX=true`. اگر درگاه انتخابی پیکربندی نشده باشد، سیستم خودکار به کارت‌به‌کارت برمی‌گردد. UI سبد خرید بر اساس `paymentProvider` در `/api/settings/public` خودش را تنظیم می‌کند (نیاز به فیش یا هدایت به درگاه).

**قواعد ایمنی:** وضعیت پرداخت هرگز از query string باور نمی‌شود؛ callback همیشه با provider verify می‌شود و تسویه ایدمپوتنت است.

## ۸. سئو (SEO)

- Metadata کامل: title template، description، canonical **به‌ازای هر صفحه** (canonical سراسری اشتباه حذف شد)، Open Graph، Twitter Card، `themeColor`, `viewport`, verification (env: `GOOGLE_SITE_VERIFICATION`).
- JSON-LD امن (escape شده): `Organization`, `WebSite + SearchAction`, `Product + Offer + AggregateRating`, `BreadcrumbList`, `CollectionPage/ItemList`, `FAQPage`. قیمت به ریال (`IRR`) طبق استاندارد.
- `sitemap.xml` پویا (محصولات با تصویر و lastModified، دسته‌ها، صفحات ثابت) و `robots.txt` (بستن داشبورد، API، حساب، سبد و URLهای فیلتر/جستجو) + `manifest.webmanifest`.
- صفحه‌ی محصول ناموجود → **HTTP 404 واقعی** (نه soft-404).
- URLهای فیلتر/جستجو/مرتب‌سازی `noindex,follow`؛ صفحه‌بندی canonical مستقل دارد.
- `h1` یکتا در هر صفحه، حذف `<main>` تودرتو، لینک‌های فوتر شکسته (about/contact/faq/orders) به صفحات واقعی وصل شدند.
- تصاویر با `next/image` و `alt`؛ فونت محلی با `display: swap`.

## ۹. نیازمندی‌های غیرکارکردی

- **امنیت:** جداسازی نقش‌ها، عدم نشت `purchaseCost`/`supplierIds` در API/HTML عمومی، ریدایرکت امن پس از ورود (بدون open redirect)، اعتبارسنجی آدرس فیش، محدودیت نرخ، رمز scrypt، کوکی HttpOnly/SameSite.
- **قابلیت اطمینان:** تلاش مجدد هنگام تداخل، ثبت رویدادهای تحلیلی به‌صورت best-effort (هرگز ورود/سبد/سفارش را خراب نمی‌کند).
- **کارایی:** سبد خرید بدون خواندن مجدد داده، cache عمومی `/api/products`، بدون commit اضافه‌ی GitHub در مسیر سفارش.
- **دسترس‌پذیری:** RTL، aria-label دکمه‌ها، نقش `alert/status` برای پیام‌ها.

## ۱۰. متغیرهای محیطی

`GITHUB_OWNER, GITHUB_REPO, GITHUB_BRANCH, GITHUB_DATA_PATH, GITHUB_TOKEN, AUTH_SECRET (≥۱۶ کاراکتر), PASSWORD_RESET_CODE, NEXT_PUBLIC_SITE_URL, PAYMENT_PROVIDER, ZARINPAL_MERCHANT_ID, ZARINPAL_SANDBOX, GOOGLE_SITE_VERIFICATION`.

## ۱۱. ریسک‌ها و محدودیت‌های شناخته‌شده

| ریسک | راهکار |
|---|---|
| GitHub به‌عنوان دیتابیس: محدودیت نرخ و سرعت، ترافیک بالا | مهاجرت به PostgreSQL با حفظ رابط `github.ts` (لایه‌ی repository) |
| ریپوی داده **باید Private** باشد (شامل کاربران/رسیدها) | تنظیم ریپو؛ برای رسید در ریپوی خصوصی، سرویس فایل (S3/R2) یا endpoint احراز‌شده لازم است |
| کد بازیابی رمز مشترک (`PASSWORD_RESET_CODE`) | جایگزینی با OTP پیامکی (فاز بعد) |
| رویدادهای تحلیلی به‌صورت commit ذخیره می‌شوند (حداکثر ۵۰۰۰) | انتقال به سرویس تحلیل/دیتابیس |
| Rate limit در حافظه‌ی هر instance است | Redis/Upstash در مقیاس بالا |
| درگاه زرین‌پال تست‌نشده در محیط واقعی | تست Sandbox قبل از فعال‌سازی |
| فایل `ADMIN_CREDENTIALS.txt` و رمز seed | قبل از production حذف/تغییر رمز؛ فایل در `.gitignore` قرار گرفت |

## ۱۲. نقشه‌ی راه پیشنهادی

1. **قبل از انتشار:** `npm install && npm run build`، تغییر رمز ادمین، ریپوی Private، تنظیم env، تست کامل سفارش.
2. **نسخه ۲.۱:** فعال‌سازی زرین‌پال، OTP پیامکی، ایمیل/پیامک وضعیت سفارش.
3. **نسخه ۲.۲:** نظرات و امتیاز، کد تخفیف، URL محصول با slug فارسی، مهاجرت دیتابیس.

## ۱۳. چک‌لیست پذیرش MVP

- [ ] ثبت‌نام/ورود/خروج و بازیابی رمز
- [ ] افزودن به سبد (مهمان و کاربر) و ادغام پس از ورود
- [ ] ثبت سفارش کارت‌به‌کارت با فیش و آدرس ذخیره‌شده
- [ ] تأیید پرداخت توسط مدیر → ثبت درآمد + وضعیت سفارش مشتری

- [ ] مشتری نتواند `/dashboard` و `/api/admin/*` را باز کند
- [ ] پاسخ `/api/products` فاقد `purchaseCost`
- [ ] `sitemap.xml`, `robots.txt`, JSON-LD در Rich Results Test معتبر
